Jag siktar på VG.


1. Vad är pull respektive push?
Pull används när man vill hämta ändringar från en remote branch och integrera de i lokala branchen.
Push används när man vill skicka lokala ändringar till en remote repository.

2. När använder man log respektive status?
Log används när man vill titta på commit historiken.
Status används när man vill ta reda på vilken plats (stage) filerna ligger. 
Till exempel om filerna behövs committa eller om de är i staging eller inte.


3. Vad är en Git branch och varför är de viktiga?
Git branch är en separat utvecklingslinje som skiljer sig från main/master branchen.
Branch är viktigt eftersom det hjälper till att få ordning när man arbetar med olika funktioner i samma projekt.
eller särskilt när man arbetar med andra utvecklare i samma projekt.

4. Det finns flera sätt att rulla tillbaka koden till ett tidigare tillstånd. 
Förklara skillnaden och motivera när man skulle använda den ena eller andra metoden. 
Ge exempel på de kommandon du använder för att göra detta och vissa att det fungerar, vilken output du fick från git-kommandona.

git restore - används för att återställa en fil till en tidigare version. 
Det är bara fil i working directory som är påverkad av den kommandon.
git restore är lämpligt att använda när man vill ångra en fil antingen i working director eller staging.

git reset - flyttar commit historiken till en tidigare tillstånd. Det finns 3 olika flaggor som kallas för soft, mixed och hard.
Commit historiken påverkas när man använder alla 3 flaggor. 
Soft - behåller ändringar i stagin area och i working directory.
mixed - behåller ändringar bara i working directory.
hard - alla ändringar i stagin och working area påverkas. 
Den ska ta bort alla nuvarande ändringar och istället ha de ändringar från tidigare committen.

git reset bör användas försiktigt och när man verkligen behöver börja om från ändringar i sista committen.
Det är bättre att använda git reset --hard bara när man arbetar ensam i ett projekt.

exempel:
$ cat >> README.md 
Read me now!

$ cat README.md 
Read me first
Read me now!

$ git status
On branch test-branch
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   README.md

no changes added to commit (use "git add" and/or "git commit -a")

$ git commit -am "update readme.md"
[test-branch 1626214] update readme.md
 1 file changed, 1 insertion(+)

$ git status
On branch test-branch
nothing to commit, working tree clean

$ cat README.md 
Read me first
Read me now!

$ git log --oneline
1626214 (HEAD -> test-branch) update readme.md
459e48a adding readme.md

$ git reset --hard HEAD~1
HEAD is now at 459e48a adding readme.md

$ cat README.md 
Read me first

$ git log --oneline
459e48a (HEAD -> test-branch) adding readme.md
$ 


git revert - används för att gå tillbaka till en tidigare commit men på det här fallet commit historiken behållas.
Git revert skapar en ny commit samma som den tidigare commiten man vill gå tillbaka till. 
Det är bättre att använda Git revert när man arbeterar i ett group eller team i ett projekt. 
Då kan alla andra utvecklare veta om vad som hände i utvecklings historiken.

exempel:

$ cat >> README.md 
Read me next

$ git status
On branch test-branch
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   README.md

no changes added to commit (use "git add" and/or "git commit -a")

$ cat README.md 
Read me first
Read me next

$ git commit -am "add second line to readme.md"
[test-branch 81d5cc8] add second line to readme.md
 1 file changed, 1 insertion(+)

$ git log --oneline
81d5cc8 (HEAD -> test-branch) add second line to readme.md
459e48a adding readme.md

$ git revert 81d5cc8
[test-branch fdf5eb4] Revert "add second line to readme.md"
 1 file changed, 1 deletion(-)

$ cat README.md 
Read me first

$ git log --oneline
fdf5eb4 (HEAD -> test-branch) Revert "add second line to readme.md"
81d5cc8 add second line to readme.md
459e48a adding readme.md
$ 


VG Delen:

1. Beskriv och jämför hur man kan använda git rebase och git merge i ett
scenario där flera utvecklare jobbar på olika feature branches.

Git merge används för att sammanfoga olika delar i projekt till ett.
Ett exempel scenario:
En utvecklings team som har har fått ett krav för att bygga en webbsida. Och en function som "Login" är delas med 3 utvecklare. En som är ansvarig för "User Creation" delen och den andra som är ansvarig för "Login Validation" delen och en annan som är ansvarig för "Forgot Password" delen.
De gör sin utveckling på sin egen branch och sen efter "Login" och "Forgot Password" delarna är färdig måste de sammanfoga de delarna med "User Creation" delen. Då används git merge.

Git rebase används också för att integrera ändringar från en branch till en annan men den kan användas för att ha en linjär utvecklings historik.
Ett exempel scenario:
Jag bygger på exempel ovanför. Efter att ha gjort merge arbetar en utvecklare på en bugg i första delen - "User Creation". Efter den är färdig kan man använda git rebase i sin branch för att inkludera buggfixen med hela "Login" function.

2. Diskutera fördelarna och nackdelarna med båda teknikerna, samt hur de
påverkar historiken.
Git merge bevarar hela den faktiska historiken som den skedde medan git rebase skriver om commit historiken för att skapa en linjär historik.

En fördel med git merge är att historiken ändras inte och det visar hur koden integrerade.
Däremot en nackdel med merge är att historiken kan bli svårt att följa som en linjär.
Medan är det lättare att följa historiken med git rebase.
Den rekommenderade sätt att använda dem är genom att använda git rebase bara i sin egen branch och att använda alltid git merge med delade branch.
